# R2 계획서 — 실기기 첫 시험에서 장치를 못 읽는 문제

작성: 총괄, 2026-11-24

## 1. 사용자 보고(윈도우 회사 PC, R1 exe 첫 실행)
- 내 마이크·상대방 소리 목록이 비어 있음. [장치 새로고침]을 눌러도 같음.
- [녹음 시작]·[중지]가 비활성. 오류 창은 뜨지 않음.
- 사용자 요청: 장치는 윈도우에서 쓰는 것을 그대로 받아오게 할 것.

## 2. 총괄의 원인 추정(미확인)
증상은 `gui._init_backend` 의 실패 경로와 일치한다(오류 창 없이 상태줄만 바꾸고 시작 버튼 비활성, 새로고침은 backend 가 없어 아무 일도 안 함). 즉 `SoundcardBackend()` 생성(= `_run_in_mta` 스레드에서 `import soundcard`)이 실패했을 가능성이 높다.
유력 후보: `_run_in_mta.work()` 가 먼저 `com_init()`(CoInitializeEx → S_OK)을 부른 뒤 같은 스레드에서 soundcard 를 불러온다. soundcard 의 `_COMLibrary` 가 다시 CoInitializeEx 를 부르면 S_FALSE(1)가 돌아오고, soundcard 가 이것을 오류로 처리해 예외를 낼 수 있다. CI 자체 시험은 주 스레드에서 직접 `import soundcard` 만 해서 이 경로를 지나지 않는다.
이것은 추정이다. 구현자는 soundcard 소스로 확인하고, **윈도우 CI 에서 실제 경로를 재현**해 확정한다.

## 3. 할 일
1. **재현 장치**: `--selftest` 에 "화면이 쓰는 것과 똑같은 경로"(Tk 루트 생성 뒤 `default_backend()` → 목록 읽기 → 기본 장치 id 조회)를 넣는다. 불러오기·초기화 실패는 실패로 판정하고, 장치가 0개인 것(CI 러너)만 참고로 둔다. 먼저 수정 없이 이 검사만 올려 CI 에서 실패가 재현되는지 본다(총괄이 CI 결과를 확인해 알려 줌).
2. **원인 수정**: 확인된 원인에 맞춰 고친다. COM 초기화 순서·스레드 규칙(F1)은 유지한다.
3. **화면**
   - 장치 선택 맨 위에 "자동(윈도우에서 쓰는 장치 그대로)"을 두고 기본값으로 한다. 이 선택은 장치 목록을 읽지 못해도 녹음을 시작할 수 있어야 한다(녹음 스레드가 기본 장치를 직접 연다). 특정 장치 고르기는 선택 사항.
   - 장치 계층을 못 열면 숨기지 말고 화면에 원인 문구를 보여 주고, [오류 내용 복사] 버튼(버전·윈도우 버전·오류·최근 로그 30줄, 회의 내용 없음)을 둔다. [장치 새로고침]은 backend 생성부터 다시 시도한다.
   - 감사 N3(기본 장치를 고정할 방법 없음)는 위 구조로 함께 해결한다.
4. N1(녹음 시작 실패 경로에서 스레드를 멈추지 않음)을 함께 고친다(같은 시작 경로).

## 4. 제약
- R1 계획서 5절과 같다. `meeting-recorder/` 와 빌드 워크플로만, 작업 브랜치 `claude/wizardly-lovelace-ojns73` 만 push. 실행 중 외부 접속 없음.
- 실기기를 볼 수 없으므로, 검증한 것과 못 한 것을 구분해 적는다. CI 러너에는 소리 장치가 없다는 한계를 명시한다.

## 5. 완료 기준
- 수정 전 코드에서 새 자체 시험이 CI 에서 실패하고(재현), 수정 뒤 성공한다. 재현되지 않으면 그 사실과 다음 가설을 보고한다.
- pytest 통과, 윈도우 빌드와 `--selftest` 성공.
- 장치 목록 실패를 흉내 낸 시험에서 "자동"으로 녹음이 시작된다.
