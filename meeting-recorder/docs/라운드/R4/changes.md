## 2-1. 모델 선택 — **'정확' 은 large-v3-turbo 로 채택(medium 은 넣지 않음)**

### 비교표(같은 표본, 언어 판별 small, 용어 힌트 없음, 4스레드)

| 항목 | small(빠름) | medium | **large-v3-turbo(정확)** |
|---|---|---|---|
| 영어 단어 오류율(FLEURS 30 + 합성 12문장, 217초) | 0.052 | 0.042 | **0.040** |

| 혼합 언어 6세트 64발언: 발언별 언어 정답 / 번역(영어→한글) | 64/64 / 0 | 64/64 / 0 | 64/64 / 0 |
| 혼합 언어 6세트 오류율 | 0.100 | 0.074 | **0.062** |
| 처리 시간: 영어 10분 2트랙(표본 반복) | 259초 | 576초 | **240초** |
| 처리 시간: 42초 2트랙 표본 | 10.5초 | 19.3초 | 17.1초 |
| 처리 시간: 영어 217초 / 한국어 109초 / 혼합 320초 | 36 / 21 / 66초 | 78 / 43 / 133초 | 53 / 25 / 110초 |
| 메모리 최고치(10분) | 1,573MB | **3,861MB** | 2,848MB |
| 메모리 최고치(그 밖) | 820~1,090MB | 2,630~2,810MB | 2,520~2,660MB |
| 모델 파일 | 484MB | 1,528MB | 1,618MB |

- 결정 규칙(총괄) 확인:
  - ① 한국어·영어 정확도: turbo ≥ medium(영 0.040 vs 0.042, 한 0.058 vs 0.096, 혼합 0.062 vs 0.074). **충족**.
  - ② 처리 시간: turbo/medium = 0.42~0.89배로 1.2배 이내. **충족**.
  - ③ 메모리 최고치: 2.85GB 로 4GB 이하. **충족**.
  - → '정확' = turbo, medium 은 묶음에 넣지 않습니다.
- medium 이 10분에서 느리고 메모리가 큰 것은 반복 표본에서 whisper 반복 재시도(fallback)가 많이 일어난 영향이 큽니다. turbo 는 디코더가 4층이라 재시도 비용이 작습니다.
- 출처·신뢰성:
  - turbo 변환본은 `mobiuslabsgmbh/faster-whisper-large-v3-turbo`(커밋 0a363e9) 입니다. 설치된 faster-whisper 1.2.1 의 `utils._MODELS` 가 'large-v3-turbo' 이름으로 이 저장소를 씁니다.
  - 원본 `openai/whisper-large-v3-turbo` 의 CTranslate2 fp16 변환(모델 카드에 변환 명령 기재)이고, 라이선스는 둘 다 MIT 입니다.
  - 5개 파일 해시를 `mrec/models.py` 에 고정했고, 빌드 때 `tools/download_models.py` 가 확인합니다.
  - turbo 는 멜 128개라 `preprocessor_config.json` 도 동봉합니다.
- 번역 없이 옮기는지: 혼합 6세트에서 영어→한글 0, 한국어→영문 0 입니다(언어 고정 방식과 호환).
- full large-v3 제외 근거: 파일 3.09GB(fp16, turbo 의 1.9배)이고 디코더가 32층(turbo 4층)입니다. 공개 자료에서 turbo 가 large-v3 보다 수 배 빠르다고 알려져 있어, 8코어 CPU 에서 실용 범위를 벗어난다고 봤습니다(직접 측정하지 않음).
- 16GB 환경 해석: turbo 2.8GB·small 1.6GB 모두 여유가 큽니다. 7.7GB 노트북에서도 4GB 목표 안입니다.

### 언어 판별 모델(R3 발언 단위 판별)

| 판별 모델(옮기기 turbo) | 혼합 64발언 언어 정답 | 한국어→영문 | 판별 시간 |
|---|---|---|---|
| **small(채택)** | **64/64** | 0 | 20.2초 |
| turbo | 56/64 | 6 | 53.8초 |

- 판별은 small 로 하고, 판별이 끝나면 small 을 내린 뒤 turbo 를 올립니다. 두 모델을 동시에 메모리에 두지 않습니다(`pipeline.run`).
- '빠름' 은 small 하나로 판별과 옮기기를 모두 합니다(다시 읽지 않음).
- R3 N1(확실하지 않은 짧은 발언): 판별 모델이 small 그대로라 동작이 달라지지 않습니다. 이번에 따로 바꾸지 않았습니다.

### 화면·처리
- '처리 품질': **정확(기본)** / **빠름**. 설정에 저장되고, 회의 폴더 다시 처리·음성 파일 처리에도 지금 고른 품질을 씁니다.
- 예상 처리 시간 안내: 정확 '녹음 길이의 약 0.4배', 빠름 '약 0.3배'. 4코어 측정 기준이며 화면에도 그렇게 적었습니다.
- 2트랙 10분 = 240초 → 0.40배, 42초 표본 0.41배, small 42초 표본 0.25배를 근거로 했습니다.

### CPU 스레드(가상 PC 8코어 대비)
- 이전: faster-whisper·화자 분리 모두 `min(8, 논리 코어)` 였습니다(8코어면 8개 전부 사용).
- 지금: `sysinfo.compute_threads()` = **논리 코어 - 1**(화면 응답용으로 1개 남김), 1~8. 4코어 → 3, 8코어 → 7, 16코어 → 8 이고, 시험용으로 `MREC_THREADS` 가 우선합니다.
- 말소리 찾기(VAD)는 1스레드 그대로입니다.
- 스레드 수별 처리 시간(turbo, 42초 2트랙 표본, 4코어 컨테이너): 1 → 31.5초, 2 → 22.7초, 3 → 17.7초, 4 → 16.5초. 8코어에서의 값은 측정하지 못했습니다.

## 2-2. 분야 용어

### 힌트 방식 확인(faster-whisper 1.2.1 소스)
- `initial_prompt`: `condition_on_previous_text=False`(지금 설정) 이면 묶음의 **첫 30초 창에만** 쓰입니다. `generate_segments` 1143~1147줄, 1372~1383줄에서 프롬프트를 초기화하기 때문입니다.
- `hotwords`: `get_prompt` 1542~1548줄에서 **30초 창마다** 프롬프트 앞에 붙고, 최대 223토큰(max_length//2-1)에서 잘립니다.
- 프롬프트가 길수록 한 창에서 만들 수 있는 출력이 줄어듭니다(448 - 프롬프트).
- → **hotwords 채택**. 용어 단위로 **120토큰**(현재 파일에서 앞의 33개)까지만 쓰고, 나머지 개수는 화면·로그에 알립니다.
- 적용 언어: **영어 묶음만**. 한국어 묶음에 줄 때 small 은 글자 오류가 0.125 → 0.133 으로 나빠졌고, 223토큰에서 처리 시간이 13 → 122초로 늘었습니다(반복 생성).
