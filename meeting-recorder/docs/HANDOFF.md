# 인계 문서 — 회의 녹음·기록 프로그램

마지막 갱신: 2026-11-26 (R6 종료 시점)

이 문서 하나로 다음 작업자가 이어갈 수 있게 정리했습니다. 사용 방법은 `meeting-recorder/README.md`, 라운드별 상세 기록은 `docs/라운드/R1`~`R6` 에 있습니다.

## 1. 무엇을 하는 프로그램인가
- 윈도우 PC 에서 화상회의를 녹음합니다. 내 마이크와 스피커로 나오는 상대방 소리를 따로 저장합니다.
- PC 안에서만 글로 옮기고(실행 중 인터넷 접속 없음), 발언자를 나눠 대화록을 만듭니다.
- 요약·교정은 프로그램이 하지 않습니다. 결과 파일을 사용자가 쓰는 AI 도구에 넣어 처리합니다.

## 2. 현재 상태
| 항목 | 상태 |
|---|---|
| 녹음(내장 마이크, USB 헤드셋 마이크, 스피커 루프백) | 실기기 확인됨 |
| 실제 화상회의 통화 녹음 | 실기기 확인됨(1:1 통화) |
| 한국어·영어 발언 단위 구분 | 표본 검증, 실기기 사용 중 |
| 정확 모델(large-v3-turbo) | 표본 검증 |
| 분야 용어 힌트, 교정용 결과 파일 4종 | 표본 검증 |
| 긴 회의(1시간 이상), 참석자 여러 명 | 실기기 미확인 |
| 장치 끊김 뒤 자동 재연결 | 가짜 장치로만 확인 |

라운드 요약
- R1 골조 / R2 윈도우에서 소리 장치를 못 읽던 문제 / R3 영어가 한국어로 번역되어 적히던 문제 / R4 turbo 모델·용어 힌트·결과 파일 / R5 일부 마이크를 열지 못하던 문제·장치 점검 / R6 묶음 크기 줄이기·덧붙는 글 방지·짧은 한국어 발언 보완.
- R6 의 병합 여부와 최종 감사 결과는 `docs/라운드/R6/결과.md` 를 보십시오.

## 3. 프로그램(exe 묶음)을 다시 만드는 방법
내려받기 링크는 만든 뒤 7일이 지나면 사라집니다. 필요할 때 아래 순서로 다시 만듭니다.
1. 깃허브에 로그인해 이 저장소를 엽니다.
2. 위쪽 **Actions** → 왼쪽 **회의 녹음 프로그램 윈도우 빌드** → 오른쪽 **Run workflow** → 브랜치는 기본 브랜치 그대로 두고 **Run workflow**.
3. 10~15분 뒤 초록색 체크가 된 실행을 눌러, 맨 아래 **Artifacts** 의 **MeetingRecorder-windows** 를 받습니다.
- 빌드는 두 작업으로 돕니다: 리눅스에서 turbo 모델을 8비트로 변환(결과 해시 검사) → 윈도우에서 시험·exe 빌드·자체 시험·묶음 올리기.
- 묶음은 수동 실행과 기본 브랜치 push 때만 올라갑니다. 매주 정리 작업이 최신 2개만 남깁니다.
- '모델 받기'가 오래 멈추면(30분 제한) 실행을 다시 돌리면 됩니다. 시간에 민감한 시험이 드물게 실패하면 **Re-run failed jobs** 로 한 번 다시 돌립니다.

## 4. 저장소 운영에서 주의할 것
- 저장소가 공개 상태입니다. 공개 저장소는 Actions 사용 시간과 Artifacts 저장이 무료입니다.
- **비공개로 바꾸기 전에** Artifacts(묶음 1개가 1GB 이상)를 지우십시오. 비공개 저장소는 계정의 저장 한도와 Actions 사용 시간 한도를 쓰며, 넘으면 계정의 다른 비공개 저장소 Actions 까지 멈출 수 있습니다. 윈도우 작업은 사용 시간이 2배로 차감됩니다.
- 회의 녹음·기록·용어 파일(사용자가 고친 것)은 저장소에 넣지 않습니다. 저장소의 `glossary/` 에는 공개 자료에서 모은 일반 용어만 있습니다.
- 문서·주석·커밋 메시지에 사용자의 회사·고객·환경을 추정할 수 있는 내용을 적지 않습니다.

## 5. 알려진 한계
사용자용 정리는 `README.md` 의 '알려진 한계' 절에 있습니다. 개발 관점의 요점:
- 영어 사이에 낀 2초 미만 한국어 발언은 빠질 수 있습니다(1.5초 6개 중 2개, 1초 6개 중 4개). '불확실' 조각이 이웃 언어 묶음에 들어가 글이 안 나오거나, 말소리 찾기가 못 잡기 때문입니다.
  - 이를 채우는 '다시 보기'(`Transcriber.recheck_unsure`, 설정 `recheck_unsure`)는 리눅스에서 1.5초 6/6·오기 0 이었습니다. 그러나 윈도우 CI 한 실행(45655947528)에서 짧은 말·작은 목소리 트랙의 영어 1개가 한글로 적혀 원인에서 배제하지 못했고, 그래서 **기본 끔**입니다(R6 changes.md '되돌림').
- 한 문장 안에서 한국어와 영어 단어를 섞으면 한쪽 언어로 적힙니다.
- 잡음만 있는 구간에서 turbo 가 말하지 않은 글을 만들 수 있습니다. 묶음 끝의 무음에서 생기던 덧붙임만 좁은 규칙으로 막았고, 실제 발언을 버릴 위험 때문에 넓은 거르기는 넣지 않았습니다.
- 용어 힌트는 파일 앞쪽 약 33개(120토큰)만 쓰이고 영어 발언에만 적용됩니다.
- 발언자 구분은 목소리가 비슷하거나 동시에 말하면 틀립니다.
- 장치: 믹스 형식이 정수형(PCM)인 장치는 기존 경로로 열리면 소리가 깨질 수 있다는 추정이 있습니다(실기기 사례 없음). 열기 실패가 반복되면 자원이 조금씩 샐 수 있습니다.

## 6. 다음에 할 만한 일(우선순위 순)
1. 실제 회의(1시간 이상, 참석자 여러 명)로 처리 시간·발언자 구분·용어 인식 확인.
2. 영어 전용 모델(parakeet-tdt-0.6b-v2) 혼합 구성: R6 측정에서 영어 처리 시간 0.4~0.56배, 잡음 구간 지어낸 글 0, 영어 오류율 0.037(turbo 0.040), 용어 적중 36/47(turbo 38). 묶음이 약 0.6GB 커지고, 언어 판별이 틀린 한국어 발언이 엉뚱한 영어로 적히는 위험에 대한 안전장치가 필요합니다. 사용자는 2026-11-25 에 "모델은 유지하고 용량만 줄인다"로 결정했습니다.
3. 녹음 이어하기: 일시정지/재개, 중단된 녹음에 이어 붙이기, 여러 녹음을 하나의 대화록으로 합치기(사용자 결정 대기).
4. 판 교체 시 사용자 용어 파일·설정 유지(프로그램 폴더 밖 고정 위치).
5. 이번 회의에만 쓰는 단어 입력 칸, 텍스트에서 용어 후보 뽑기.
6. 짧은 한국어 누락: 다시 보기를 윈도우에서 여러 번 돌려 영어→한글 오기 조건을 확인한 뒤 기본으로 켤지 결정(시험 `test_short_korean_recheck_on_fills_without_wrong_script` 는 한계 시험으로 둠).
7. 감사 이월 경미 건: 각 라운드 `audit/` 폴더의 findings 표 '총괄 판정' 열 참고.

## 7. 작업 방식
- 총괄이 라운드 계획서(`docs/라운드/R{n}/00_계획.md`)를 쓰고, 구현 담당이 구현·시험·`changes.md`, 감사 담당이 독립 감사(`audit/`)를 합니다. 치명·중요 지적은 수정 → 재감사(최대 2회) 뒤 병합합니다.
- 시험: `meeting-recorder/` 에서 `python -m pytest -q`. 모델이 필요한 시험은 `tools/download_models.py` 로 모델을 받은 뒤 돕니다(모델 폴더는 `MREC_MODELS_DIR` 로 지정 가능).
- 배운 점: (1) 감사 지적을 고친 변경이 실기기 경로를 깬 적이 있습니다(R2). 자체 시험은 제품이 실제로 쓰는 경로를 그대로 지나야 합니다. (2) 구현 담당은 CI 결과를 볼 수 없으니, 총괄이 감사 전에 윈도우 빌드 결과를 직접 확인해야 합니다(R6). (3) 크기·속도를 줄이는 변경은 짧은 발언·작은 목소리 같은 가장자리 조건에서 정확도를 깎기 쉽습니다. 표본에 없는 조건은 감사에서 직접 만들어 재야 합니다.
