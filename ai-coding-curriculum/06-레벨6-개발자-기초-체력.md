## 📚 핵심 개념

### 1. 웹과 HTTP (요청과 응답)

- 🧒 **비유:** 식당에서 **주문서(요청)** 를 내면 주방이 **음식(응답)** 을 줘요. 주문서에는 "어느 식당(주소), 무엇을(경로), 어떻게(방법)"가 적혀 있어요.
- 📖 **정확히:** 브라우저나 프로그램(클라이언트)이 **HTTP 요청(request)** 을 서버에 보내면 서버가 **응답(response)** 을 돌려줘요.
  - **메서드:** `GET`(가져오기), `POST`(새로 만들기), `PUT/PATCH`(고치기), `DELETE`(지우기)
  - **상태 코드:** `200` 성공, `201` 만들어짐, `400` 요청이 이상함, `401/403` 권한 없음, `404` 없음, `500` 서버 고장
  - **헤더(header):** 편지 봉투 정보, **본문(body):** 편지 내용

### 2. API와 JSON

- 🧒 **비유:** API는 식당의 **메뉴판**이에요. 메뉴판에 있는 것만, 정해진 방법으로 주문할 수 있어요. JSON은 음식을 담는 **칸 나뉜 도시락통**이에요.
- 📖 **정확히:** **API**는 프로그램끼리 대화하는 약속이에요. 웹 API는 보통 HTTP로 **JSON**을 주고받아요. JSON은 `{"이름": "값"}` 모양의 글자 형식이에요. Python의 `dict`/`list`와 거의 같아요. roadmap.sh backend-beginner 로드맵은 APIs → JSON APIs → REST → 인증(authentication) → JWT 순서로 배우도록 해요.

```json
{"id": 1, "title": "우유 사기", "done": false, "tags": ["장보기"]}
```

### 3. 테스트 (Test)

- 🧒 **비유:** 받아쓰기 **정답지**예요. 코드를 고칠 때마다 정답지로 채점하면, 예전에 맞던 게 틀려졌는지 바로 알아요.
- 📖 **정확히:**
  - **단위 테스트(unit test):** 함수 하나를 검사
  - **통합/E2E 테스트:** 여러 부분을 함께, 사용자처럼 검사
  - Python에서는 `pytest`를 많이 써요. `test_`로 시작하는 함수 안에 `assert`를 써요.
  - 에이전트에게 테스트는 **"완료 기준을 코드로 쓴 것"** 이에요. roadmap.sh는 "**버그를 찾으면 그 버그를 드러내는(실패하는) 테스트부터** 쓰게 하라", "테스트가 생기면 **꾸준히 리팩터링**하라"고 해요.

```python
# tests/test_math.py
from mymath import add

def test_add():
    assert add(2, 3) == 5
```

### 4. 디버깅 (Debugging)

- 🧒 **비유:** **탐정 놀이**예요. ① 사건 재현 → ② 용의자(가설) 세우기 → ③ 증거(로그) 모으기 → ④ 범인 확정 → ⑤ 다시는 안 생기게 덫(테스트) 놓기.
- 📖 **정확히:**

| 단계 | 할 일 | 도구 |
|---|---|---|
| 재현 | 매번 같은 방법으로 버그가 나게 만들기 | 실패 테스트 |
| 가설 | "여기가 문제일 것 같다" 2~3개 | 에러 메시지, traceback |
| 증거 | 값 찍어 보기 | `print`, `logging`, 디버거(`breakpoint()`) |
| 수정 | **근본 원인** 고치기 (에러 숨기기 ❌) | |
| 예방 | 테스트를 남기기 | pytest |

roadmap.sh vibe-coding 로드맵의 AI 활용 요령: "**에러 메시지를 프롬프트에 넣어라**", "계속되면 **가능한 원인 목록**을 만들게 하라", "**로그를 넣게** 하라".

### 5. 코드 읽기 (Code reading)

- 🧒 **비유:** 처음 가는 **큰 도서관**에서 먼저 **안내도(입구, 층별 안내)** 를 보고, 필요한 책장으로 가요.
- 📖 **정확히:** 남이 쓴 코드를 읽는 힘은 에이전트 시대에 더 중요해요(에이전트가 쓴 코드도 "남의 코드"예요). 순서는 **README → 진입점(main) → 폴더 구조 → 테스트 → 핵심 함수**. MIT Missing Semester 연습 2번은 "**AI 코딩 에이전트로 낯선 코드베이스를 탐색해 보라**"예요. charlax는 "코딩 실력을 확실히 늘리는 한 가지 방법: **코드 읽기!**"를 소개해요.

### 6. 보안 기초 (Security basics)

- 🧒 **비유:** 집 **열쇠를 현관 매트 밑에 두지 않기**예요. 비밀번호를 코드에 적으면 GitHub에 올리는 순간 온 세상이 봐요.
- 📖 **정확히:**

| 규칙 | 방법 | 출처 |
|---|---|---|
| 비밀 정보를 코드에 쓰지 않기 | **환경 변수(env)** 사용, `.env`는 `.gitignore`에 | roadmap.sh vibe-coding |
| 에이전트가 비밀 파일을 못 읽게 | Claude Code `deny: Read(./.env)` (모든 모드에서 적용) | Claude `permissions.md` |
| 보안 점검을 명시적으로 부탁 | "보안 감사(security audit)를 해 줘", Claude `/security-review` | roadmap.sh, Claude `commands.md` |
| AI 출력의 보안 버그 검토 | 사용자 입력 검사, 비밀 노출, 위험한 명령 | Missing Semester |
| 위험한 자동 모드는 격리 환경에서 | VM, 컨테이너 | Missing Semester |

### 실습 1. HTTP 눈으로 보기 (30분, AI 없이)

```bash
# 공개 API에 GET 요청 보내기 (-i: 응답 헤더도 보기)
curl -i https://api.github.com/repos/agentsmd/agents.md
```
1. 첫 줄의 **상태 코드**를 찾아요.
2. 본문(JSON)에서 `stargazers_count`와 `description`을 찾아요.
3. 없는 저장소 주소로 바꿔 요청해 보고 상태 코드를 비교해요.

```bash
# 내 컴퓨터에 작은 웹 서버 띄우기
cd ~/ai-practice && python3 -m http.server 8000
# 브라우저에서 http://localhost:8000 열기 → 터미널에 찍히는 요청 기록 보기 → Ctrl+C로 끄기
```

✅ **Done when:** 성공(200)과 실패(404)의 상태 코드를 직접 봤고, 서버 로그에서 `GET` 요청 줄을 찾았어요.

### 실습 2. Python으로 API 부르기 (45분, 🔴 선생님 모드)

`github_info.py`를 **직접** 써요.

### 실습 3. 할 일 앱을 웹 API로 키우기 (90분, 🟢 위임 + 검증)

레벨 5의 `todo-app`에서 브랜치를 만들어요: `git switch -c web-api`

계획 모드에서:
```text
# 목표
todo 앱에 간단한 HTTP API를 추가하고 싶어.

# 맥락
- 지금 구조는 @SPEC.md 와 CLAUDE.md(또는 AGENTS.md)를 봐.
- 나는 HTTP 메서드와 상태 코드를 막 배웠어.

# 제약
- 많이 쓰이는 가벼운 방법을 써 줘. 새 라이브러리가 필요하면 먼저 이유를 말하고 내 허락을 받아.
- 할 일 데이터는 JSON 파일에 저장해.
- 기존 테스트는 고치지 마.

# 완료 기준 (Done when)
- GET /todos → 200과 JSON 목록
- POST /todos → 201, 제목이 비어 있으면 400
- DELETE /todos/<id> → 없는 id면 404
- 위 경우마다 자동 테스트가 있고, 전체 테스트가 통과함
- 내가 직접 확인할 수 있는 curl 명령 예시를 마지막에 적어 줘

먼저 계획만 보여 줘.
```

계획 승인 → 구현 → **내가 직접** 서버를 띄우고 curl로 4가지 경우를 확인 → `git diff` 읽기 → 커밋.

✅ **Done when:** 내 터미널에서 curl로 200/201/400/404를 모두 직접 봤고, 테스트가 통과했어요.

### 실습 6. 비밀 지키기 (40분)

1. `.env` 파일을 만들고 가짜 키를 넣어요: `echo "API_KEY=fake-123" > .env`
2. `.gitignore`에 `.env`를 추가하고 `git status`에 `.env`가 안 보이는지 확인해요.
3. 코드에서는 `os.environ`으로 읽게 바꿔요.
4. (Claude Code) `.claude/settings.json`에 아래를 넣고, "`.env` 파일 내용을 보여 줘"라고 부탁해서 **거절되는지** 확인해요.
```json
{
  "permissions": {
    "deny": ["Read(./.env)", "Read(./.env.local)", "Read(./secrets/**)"]
  }
}
```
5. 보안 점검을 부탁해요:
```text
이 저장소를 보안 관점에서 검토해 줘. 비밀 정보 노출, 사용자 입력 검사 누락, 위험한 명령 실행만 봐 줘.
스타일 지적은 빼고, 각 문제마다 파일:줄과 실제로 문제가 되는 시나리오를 적어 줘.
```
(Claude Code는 `/security-review`도 있어요.)

✅ **Done when:** `.env`가 git에 안 올라가고, 에이전트가 `.env` 읽기를 거절당했고, 보안 점검 결과 중 1개 이상을 직접 확인(또는 "문제 아님" 판단)했어요.

## 🧠 스스로 확인 문제

1. `404`와 `500`의 차이는?
2. 버그를 고칠 때 "실패하는 테스트부터" 쓰는 이유는?
3. 디버깅 5단계를 말해 보세요.
4. API 키를 코드에 직접 쓰면 왜 위험한가요? 대신 어떻게 하나요?
5. "빌드 에러를 고쳐 줘" 대신 어떻게 말해야 에러를 숨기는 꼼수를 막을 수 있나요?

<details><summary>정답 보기</summary>

1. `404`는 요청한 것이 없다는 뜻이에요(주소 문제). `500`은 서버 안에서 고장이 났다는 뜻이에요(서버 코드 문제).
2. 버그가 정말 있는지 확인(재현)하고, 고친 뒤 통과하는 것으로 "고쳐졌다"를 증명하고, 다시 생기지 않게 막기 위해서예요.
3. 재현 → 가설 → 증거(로그) → 근본 원인 수정 → 테스트로 예방.
4. 저장소에 올리면 누구나 볼 수 있고, git 기록에도 남아요. 환경 변수와 `.env`(git에서 제외)를 쓰고, 에이전트의 읽기도 deny로 막아요. 이미 올렸다면 키를 바꿔요.
5. "고치고 빌드가 성공하는지 확인해. 에러를 숨기지 말고 근본 원인을 고쳐." (Claude 문서 예시)

</details>

| 디버깅 소용돌이: 같은 시도를 계속 반복 | 멈추고, 가설을 적고, 새 세션 |
| 테스트 없이 "잘 되는 것 같아요" | 테스트·curl로 증거 남기기 |
| 비밀 키를 프롬프트나 코드에 붙여넣기 | 환경 변수 + deny 규칙 |
| AI가 추천한 낯선 라이브러리를 바로 설치 | 이유를 묻고, 많이 쓰이는 것인지 확인 (roadmap.sh: 인기 있는 기술 선택) |
